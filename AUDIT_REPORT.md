## 2. Three distinct kinds of "not working"

### A. Marked stubs (270 files) — import-compatible fakes
Every one looks like `core/agent_executor.py`:

```python
def __getattr__(name):
    class DynamicStub(metaclass=DynamicMeta):
        def __call__(self, *a, **k): return self
        def __getattr__(self, item): return DynamicStub()
        async def __aenter__(self): return self
    return DynamicStub()
```

Any `from x import y` succeeds and yields an object that swallows every call,
attribute access and `await`. This is why imports are green, collection is green
and the architecture suite is green while behavior is missing.

## 5. WHY it is like this (root cause analysis)

1. **Seed-commit scaffolding, not decay.** `git log` shows every stub file has exactly
   one revision, created in `dd4a645 "Initial Jarvis build"`. The bodies were
   auto-reconstructed from module names + test contracts; the real code never entered
   git. Hence `recoverable_from_git: null` for 400/403 entries.
2. **Silent-failure design choice.** The `DynamicStub` module `__getattr__` was chosen so
   imports/architecture gates stay green while work proceeded module-by-module
   (`MODULAR_AUDIT_PLAN.md` 12-module plan). It worked as a scaffold and stopped
   working as a system: failures now surface as `NoneType` TypeErrors 1,500 tests deep.
3. **Selective engineering attention.** What a human/agent actually touched is real
   (desktop, browser, belief/strategy/research/coding from the last ~10 commits).
   What was only ever "specified by tests" stayed a stub (workflow, routes, plugins,
   opportunity, governance, benchmark, model_providers, self_modification…).
4. **An unfinished de-poisoning campaign exists.** `scripts/stub_cleanup.py`,
   `scripts/count_stubs.py` ("the single progress metric: the number must go DOWN"),
   `stub_inventory.json`, commit `b5273d5 "De-poison: drop 82 unreferenced stub
   modules"` — the team knows; 270 remain because they are referenced (P0) or guarded.
5. **A whole subsystem is absent.** The `assistant/` voice package was never included →
   112 test errors + dead voice paths in monitors/plugins/demo.
6. **Environment gaps** (Windows binaries missing) account for ~53 failures — genuinely
   not code bugs, but they are unmarked, so they pollute the signal.
7. **Docs over-claim.** `BROWSER_AI_STATUS.md` says "PRODUCTION_READY" while the module
   it reuses (`core/browser_manager`) is a no-op shell and `PHASE_0_1_PROGRESS.md`
   claims deletions that are still present (`core/legacy/control_loop.py`).

## 6. Comparison with shipped device-control AI systems (products, not papers)

### The reference systems (as of 2026-09/10)
- **OpenAI Dots** (DevDay, 2026-09-29): always-on agents, each with its **own cloud VM
  (computer + browser)**, 4,000+ connected apps, GPT-6 Astra, ChatGPT "Space"
  human/agent collaboration, Microsoft Agent 365 governance; sensitive actions require
  approval clicks. Its **system card shows boundary-violation flag rates roughly
  double as tasks get longer** — i.e. even OpenAI treats long-horizon autonomy as an
  open safety problem.
- **OpenAI ChatGPT agent (ex-Operator)**: hosted VM with browser + terminal, confirmation
  gates; *no* access to your local machine/files/network.
- **Anthropic Claude computer use / Claude for Chrome / Claude Code**: strongest
  grounding model (top OSWorld-Verified) shipped as a *capability* — you own sandbox,
  retries, verification, credentials, audit.
- **Google Gemini computer use / Project Mariner**: browser-first, Chrome-side.
- **Microsoft Copilot, Perplexity Computer, Meta Muse (2026-09-08), Manus**: hosted/cloud.
- **Open source local peers**: Browser Use (MIT, browser-only), Open Interpreter (AGPL,
  local code exec + OS mode), OpenClaw (open source, now enterprise via Nvidia/Red Hat),
  Simular Sai (local/VM OS-level agent).

### Honest side-by-side

| Dimension | JARVIS (this repo) | OpenAI Dots / Operator | Claude computer use | OSS local (Open Interpreter / OpenClaw) |
|---|---|---|---|---|
| Runs on **your** machine, your logged-in sessions, local files/apps | **Yes — genuine differentiator** | No: cloud VM only | Yes (your harness) | Yes |
| Scope of control | Desktop (UIA/pyautogui/psutil) + browser (Playwright) + CLI | Cloud computer + browser + 4,000 apps | Whatever your harness exposes | Code-first; GUI weaker |
| Observe→ground→act→**verify** loop | Implemented in browser/desktop layers, **but wiring fails**: 43% unit tests red, `doctor` leaks DynamicStub into runtime | Shipped, monitored, approval UX, system card | Shipped; model-level SOTA grounding | Varies; you own verification |
| Permissions / safety plane | Desktop risk tiers + consent, browser fail-closed `ApprovalGate` — but `core/governance` (5/5), `core/api_key_vault`, `core/oauth` are **stubs** | Approval prompts + boundary monitoring + enterprise governance (Agent 365) | You build it | You build it |
| Control plane: HTTP API / plugins / workflow / scheduler | **34/38, 22/22, 16/16, cron+intelligence stubbed** | The actual shipped product surface | SDK + reference containers | CLI/SDK |
| Always-on autonomy | `scheduler` partially real, `autonomous/decision/intelligence` stubbed | Core design ("keeps working between conversations") | Not the design | Optional daemons |
| Memory / learning | `memory/` + `belief` + `strategy` real; `long_term_memory` 6/7, `opportunity` 10/10 stubbed | Persistent per-dot memory, managed | Your stack | Your stack |
| Model | Model-agnostic (Ollama/OpenAI/Anthropic/Gemini via `jarvis_provider`), free/local possible | Locked to GPT-6 Astra | Claude only | Model-agnostic |
| Evidence of correctness | 20,100 green **contract** tests, **43% red behavior** tests, no end-to-end device-task eval | Eval harnesses + published system cards + usage at scale | Public benchmark leaderboards + customer harnesses | Community evals |
| Secrets/credentials hygiene | `.env`, firebase/google creds present but **git-ignored and untracked** (verified) | Vendor-managed | You manage | You manage |

### What that means
1. **JARVIS's real edge is local, full-OS access** — the thing Dots/Operator structurally
   cannot do (they are sandboxed cloud VMs). That niche is real and matches what
   Claude-computer-use and OpenClaw play in.
2. **JARVIS's deficit is not ideas, it's completion + truthfulness.** The verify/recover
   semantics, risk tiers and approval gates exist on paper and in two good modules, but
   the layers that make a system *trustworthy in production* — API surface, workflow
   engine, governance/vault, benchmark/eval, memory — are stubs, and several modules
   **return fake success** instead of failing.
3. **Green architecture gates ≠ production readiness.** OpenAI ships Dots with a system
   card that reports its own failure modes; JARVIS's equivalent (doctor, status docs)
   currently reports ✓ over DynamicStub errors.
4. **No end-to-end eval loop.** `core/benchmark` is 10/10 stubbed — without OSWorld-style
   task success measurement there is no way to know whether desktop/browser gains
   regress. This is the single biggest gap vs any shipped agent product.
